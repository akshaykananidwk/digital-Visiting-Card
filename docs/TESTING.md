## Defects found and fixed during verification

Each of these was found by a suite above, not by inspection, and each is now
covered by a regression test.

### QR format information written in reverse (critical)

The first of the two format-information copies was written least-significant
bit first, mirroring it. Decoders read that copy before the second, so whenever
the mirrored bits happened to form another *valid* format codeword, the symbol
was read with the wrong mask and could not be decoded at all — including for a
realistic card URL on a reseller domain. Both `zbarimg` and OpenCV rejected the
affected codes.

Verification after the fix: the format modules now match a reference encoder for
all 32 error-correction/mask combinations, and a 480-symbol randomised sweep
(four error-correction levels × payload lengths 1–120) decoded 480/480 with
`zbarimg`.

### QR encoder limited to symbol version 10

Payloads above roughly 120 bytes at high error correction threw instead of
encoding. A card URL on a reseller's own domain with the longest slug the
routing rules accept exceeds that, so those customers could not get a QR code at
all. The encoder now covers versions 1–40. Its capacities match the standard
exactly (2,953 / 2,331 / 1,663 / 1,273 bytes at L/M/Q/H), the added tables were
checked against the codeword-capacity invariant for all 120 version/level rows
before being applied, and symbols at versions 1 through 40 decode back to the
exact payload at every error-correction level.

The 34-entry table of version-information constants was replaced with the BCH
computation it encodes, checked against the published values.

### Mask penalty ignored overlapping finder-like patterns

Rule 3 of the mask penalty used `substr_count`, which skips overlapping matches,
so a mask that riddled a symbol with false finder patterns could score as clean.
Now counted with overlaps.

### Site broken on any hostname other than `APP_URL`

Links, assets and form actions were all generated from `APP_URL`. Reached on any
other hostname — www versus non-www, an IP, a staging alias — every asset and
form became cross-origin: the Content-Security-Policy blocked the stylesheets
and scripts, and because the session cookie is scoped to the browsing host, the
login form posted without one and was rejected as a CSRF failure. **Signing in
was impossible.**

Three changes, each with regression coverage:

* URL generation now follows the host being browsed when that host is one this
  installation answers on — the `APP_URL` host, its www/non-www counterpart, or
  an alias listed in the new `APP_TRUSTED_HOSTS`. An unrecognised `Host` header
  still falls back to `APP_URL`, so a spoofed header cannot be reflected into
  generated URLs (verified in `tests/host-urls.sh`).
* Form actions and internal redirects are root-relative, so a submission always
  returns to the host it came from and keeps its session.
* The Content-Security-Policy names the configured origin alongside `'self'`.

Reseller white-label domains were already handled separately: they are verified
against the database before the URL root is switched to them.

### Design previews blocked by the framing policy

Gallery and live-editor previews are iframes whose `src` came from `APP_URL`, so
on any other host the framed page's `frame-ancestors 'self'` rejected its own
parent and every preview was blank. Preview URLs are now same-origin.
`frame-ancestors` was also tightened from `'self'` on every page to `'none'`
except on the pages that are meant to be embedded.

### Tap targets below the thumb-friendly minimum

Service and product call-to-action buttons on the public card measured 36–39px,
and panel buttons 36px. All controls are now at least 40px, and 44px on
pointer-coarse devices.

### Authenticated pages were not actually being tested

The responsive suite treated the sign-in redirect as a passing page, which is
what hid the panel tap-target problem: with login broken by the hostname defect
above, every "authenticated" page it measured was really the login screen. The
suite now fails if an authenticated page lands on `/login`.

### Request capture crashed under CLI

`$_SERVER['argv']` is an array and was being cast to string, so any CLI entry
point that captured a request raised a fatal. Non-scalar server values are now
skipped.

### Stored XSS in the card's structured data (critical)

The Schema.org JSON-LD block was written with a plain `json_encode`. An HTML
parser does not understand JSON: the first literal `</script>` inside a script
element ends it, whatever quoting the JSON uses. A card whose city, address or
description contained `</script><script>...</script>` therefore executed
attacker JavaScript on its own public page, which is served to every visitor
and embedded in the admin and gallery previews.

Confirmed by loading the card in a real browser and observing the injected
script run. JSON destined for a script block now goes through a `json_script()`
helper that escapes the tag, ampersand and quote characters to `\uXXXX`,
leaving the JSON byte-identical once parsed but giving an HTML parser nothing
to act on. `tests/xss.php` covers it and fails if the helper is bypassed.

Every other field on the card was already escaped correctly, and a hostile
theme colour is rejected by the palette validation rather than reaching the
stylesheet.

### Oversized uploads reported as a session error

A POST larger than `post_max_size` arrives with its body discarded, so the CSRF
token disappears with it and the visitor was told their session had expired.
Someone uploading a large photo had no way to know the file was the problem.
The CSRF middleware now recognises that case and returns 413 naming the actual
limit.

### Base path taken from an untrustworthy source

The application's base path was derived from `SCRIPT_NAME` without checking it
named the front controller. Where a server reports the request path instead,
the session cookie was scoped to whatever directory the visitor happened to
enter on -- so the session did not travel with them -- and a path segment was
stripped from every route. `SCRIPT_NAME` is now used only when it names a PHP
file; a sub-directory installation is configured through `APP_URL`, which is
checked first.

## Known limitation

OpenCV's QR detector fails to read a small fraction of otherwise-valid symbols
(16 of the 480 in the sweep) at certain mask patterns, while `zbarimg` reads all
480. These symbols were checked against the standard end to end — data
codewords, padding and interleaving reproduced independently; format information
matching the published table; function patterns, capacities and PNG geometry all
correct — and the reference encoder shows the same weakness on at least one
payload. This is detector robustness on valid symbols rather than an encoding
defect, but it is recorded here rather than left unstated.
